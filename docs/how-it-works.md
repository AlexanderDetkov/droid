# How Droid works

The details behind the [README](../README.md): what Droid can do on a phone and how, what it found out about Android along
the way, how its voice models were chosen, how to build and release it, and the licenses of what it uses.

## Security

Droid gives Claude a root shell on your phone, with web access (without root, a shell with adb's rights: it can use
your apps and change settings, but not read other apps' private data). Anything it reads (web pages, messages, files) could try to steer it into doing something you didn't ask for, and as root it can read every app's data. Give it tasks you'd trust it with, and keep an eye on Watch for anything sensitive. The default instructions tell it to confirm the recipient and the content on screen before sending anything, and to ask when unsure.

**Without root, Droid keeps USB debugging on**, since its helper ends when adbd stops. A computer you plug the phone into can then ask to debug it, which still needs your OK on the phone, and some apps (banking apps, for example) refuse to run while it's on.

**Voice match** replaces your fingerprint with your voice, which is a much weaker lock. It checks how a voice sounds, not that you're the one speaking, so a recording or an AI copy of your voice can pass, and whoever passes gets everything Droid can do. In a test (below), copies of a voice made by Pocket TTS, Droid's own voice model, from one 10-second clip passed 7% of the time; better cloning tools will do better. After 3 misses in a row it pauses until the phone is unlocked. It's off until you set it up.

**Without root, Droid also turns off Android's adb authorization timeout** (as Developer options → "Disable adb authorization timeout" does), so its pairing doesn't lapse after 7 days. That also keeps any computer already allowed to debug the phone allowed until you revoke USB debugging authorizations.

**Privacy**: the agent works with whatever its provider (Anthropic, OpenAI or the one you pick in OpenCode) is sent: your requests, screenshots of the hidden screen and anything else it reads. Droid itself sends nothing anywhere except Setup's downloads and, once a day, a request for GitHub's latest release. The agent's Linux looks names up through Cloudflare's and Google's public DNS (1.1.1.1 and 8.8.8.8). Voice, voice match and the camera run on the phone.

## How it works

```
root:     Droid app ──su──▶ /data/local/droid/enter.sh ──chroot──▶ Alpine: phone-agent ──▶ claude -p (stream-json)
                              private mount namespace                 │
no root:  Droid app ──Bridge──▶ /data/local/tmp/droid/enter.sh ──proot──┤
          (the shell user,                                           └─ VdHelper (app_process, as shell): hidden display
           started over Wireless debugging)
```

Everything the hidden display needs (a VirtualDevice, launching apps on its display, input, screenshots) works as
Android's shell user, uid 2000; root is only one way to become it. The other is Wireless debugging, which an app on the
phone can use on itself, as Shizuku does. So Droid runs the same agent either way, and the app reaches it through
`Host` ([`Host.kt`](../app/src/main/java/com/adetkov/droid/Host.kt)): `su -c`, or Droid's helper.

- **`enter.sh`** enters the chroot as root inside a private mount namespace (the root manager's busybox `unshare --propagation private`). `/proc`, `/sys`, `/dev` and `/sdcard` are mounted for that run only, so nothing leaks into Android's namespaces and removing the rootfs never reaches through a mount. It also sets the run's `oom_score_adj` to 200: root shells inherit -1000 (unkillable) from the root daemon, so a runaway command would otherwise leave the kernel nothing to kill and Android would reboot.
- **`phone-agent`** starts one task: it creates a hidden display the size of your screen, prints `{"type":"agent","pid","display","port","token"}`, then runs Claude Code with stream-json in and out and only general tools (Bash, Read, Write, Edit, Grep, Glob, WebSearch, WebFetch). Besides the chat, the agent gets two texts: the app's instructions ([`system.md`](../app/src/main/assets/setup/system.md), which the app writes to `~/.droid/system.md` for this phone, with root or not, at each start) and the owner's instructions (`~/.claude/CLAUDE.md`). Claude gets `system.md` with `--append-system-prompt-file` and reads `CLAUDE.md` itself, along with its own memory; Codex and OpenCode get both in their `AGENTS.md`.
- **What the agent shows** is the agent's to design ([`Pages.kt`](../app/src/main/java/com/adetkov/droid/Pages.kt), [`PageView.kt`](../app/src/main/java/com/adetkov/droid/PageView.kt), [`system.md`](../app/src/main/assets/setup/system.md)). Its answers are Markdown that can hold any HTML, CSS and JS: an answer with HTML renders in the chat as one web page, seamless with it (no frame, the chat's background, its text set exactly like a Markdown answer: [`droid.css`](../app/src/main/assets/page/droid.css) gives plain HTML the app's font, colors as theme variables, and a few classes the agent may use, such as `option`, `primary` and `card`). The Markdown in it goes through [marked](https://github.com/markedjs/marked) 15.0.12 (MIT, `assets/page/marked.min.js`), with a line break kept as one, as in Droid's own answers; a block of HTML stays markup, indented lines included, while a part of it after a blank line that doesn't start with a tag is Markdown again (as in CommonMark: a `<div>` around a list), except inside a `<textarea>`, `<pre>`, `<script>` or `<style>`, which stays whole. The stylesheet's colors are variables named for what they're for (`--surface` a card or field, `--raised` one on a card, `--ink`/`--on-ink` a main button and its text, `--call`/`--on-call` Dash's accent and text on it), and controls get their size from padding, so a page's own padding makes a compact chip. A page's script has `droid` ([`droid.js`](../app/src/main/assets/page/droid.js)): `send(text, data)` is a message from you (the chat shows the text, the agent also gets the data), `run(command)` runs a command in the Linux and returns its output without an agent turn, `dash(feeling, words)`, `screen()` hands over the hidden screen, `open(url)`, `close()`. Each page lives at its own https origin (`p….droid.page`, served by the app), so what it keeps in localStorage is its own; `droid` reaches only those origins' main frames (androidx.webkit's message listener, not a JavaScript interface every frame gets); send, run, screen and open work only within 15 s of your tap or typing on the page (camera and microphone only for a live page, from a tap); a page answers once: after it sends or is answered its controls dim and stop acting (so a second tap can't repeat what the first did), and one from an earlier turn does too unless the agent's command still waits on it (a message, wake-up or attachment meanwhile doesn't end that); links a page navigates to open the way Chrome opens them (`intent:` only to apps that take web links); in the chat a text box is as tall as its text; and of the agent's Linux a page can load only the files its own HTML names, so it can't read the rest (the Claude sign-in, say); and it runs scripts only from its own origin (a Content-Security-Policy), so none from the web gets `droid`: the agent downloads a library into its Linux and names it by its path. Now's page fills the screen under Dash and scrolls itself. While it's on screen at its top, Droid keeps a picture of it (PixelCopy, `files/stills/<chat>/p<message>.jpg`, again after each touch) that History shows in its place, at a fixed height, and a tap on it opens the page full screen (PageActivity, which opens an answer made as an app by its message too); one with no picture is a line with its name. The chat's pages stay loaded from turn to turn (two at most: its app, and a page it waits on). A page the agent shows `--home` is its chat's app, like one in the chat. A page as tall as its content (the home screen's) passes vertical drags to the list around it, measured by the finger's moves; a touch while that list still moves stops it. A tap or drag on the chat puts the keyboard away, except a tap in a page, which may be on its own field. A page in the latest turn may set Dash. `![caption](path)` still shows a picture or file: the app copies it out of the Linux (through `enter.sh`, so the path is the agent's) into `files/shown/<chat>/`. Links an earlier Droid made buttons of (`[label](reply:text)`, `[label](screen:)`) now read as their labels. Stdin takes messages at any time; `kill <pid>` stops the task. A run with no first message within 3 minutes ends itself: the app starts one early while you talk and drops it after 2 minutes unused (and never gives one older than 2.5 minutes a message), but it can't while Android has the app frozen, and the hidden display keeps the phone from sleeping.
- **`droid`**, the agent's command ([`bin/droid`](../app/src/main/assets/setup/bin/droid), Python): `droid dash FEELING [WORDS]` sets Dash and the words beside him (`droid feelings` lists them; a JSON face, such as `{"smile": 0.6}`, works too, every number kept to the range the rig draws well); `droid show FILE [--full|--float] [--wait] [--id ID]` shows a page now, in the chat (a PAGE message), full screen ([`PageActivity`](../app/src/main/java/com/adetkov/droid/PageActivity.kt): Back, the page, a message box), or floating over the app you're in ([`FloatPage`](../app/src/main/java/com/adetkov/droid/FloatPage.kt): rising from the bottom edge with Dash peeking over it; it takes the keyboard only once touched); one that can't open there (Android lets an app open a screen from the background only with the right to draw over apps) comes as a notification that opens it; `--wait` prints what the page sends, as `{"text", "data"}`, so the agent goes on in the same turn (the app writes it to `/root/.droid/replies/ID.json`; `droid wait ID` keeps waiting; a wait that ends unanswered tells the app, and a later answer comes as a message), and `--id` shows a page again in place, full screen or floating too (one from an earlier turn moves to the end of the chat, live again); while a page waits, what the owner types in the chat's or the page's message box answers it; `droid notify TITLE [TEXT]` posts a notification the agent shapes as it likes ([`Notify.kt`](../app/src/main/java/com/adetkov/droid/Notify.kt); `droid --help` lists it all): up to three buttons, each a message to the agent or `run:COMMAND` (in the Linux, no turn), `open:URL` (a link or app), `page:FILE` (a page full screen), `chat:`, `screen:` (the hidden screen handed over) or `dismiss:`, the same for its tap; a reply field (what's typed comes as a message; the notification shows it sent, then goes, or stays if it's ongoing); a picture; a progress bar; ongoing; quiet or urgent (a channel each: From Droid, quietly, urgent); private on the lock screen; Dash's feeling as its picture; `--id` to update or take it away; `--at WHEN` to post it later (kept like a wake-up); like a page, a notification answers once (a second tap can't send or run it again; one made ongoing stays, a control to use as often as you like); `--wait` to get back, in the same turn, what the owner did: the button or tap, the reply, `dismissed` if swiped away, or what a `page:` button's page sends. Taps that open a screen go through `NoteActivity` (Android lets only an activity start one), the rest through AgentService; nothing acts from the lock screen but dismiss. The answer's own notification is the id `chat`: the agent's `--id chat` replaces it and `--cancel chat` leaves it out. `droid later WHEN MESSAGE` sets a wake-up in this chat (WHEN on the phone's clock, its time zone's rules included: `17:30`, `tomorrow 9am`, `fri 14:00`, `in 2h`; a bare hour is the next time the clock shows it) ([`Later.kt`](../app/src/main/java/com/adetkov/droid/Later.kt): an exact alarm, kept in `files/later.json`, put back when the phone restarts; its message starts a turn as the agent's own). Its events reach the app as `{"type":"droid",...}` lines in `phone-agent`'s output: the command reopens that pipe through `/proc` (`$DROID_OUT`), so they arrive at once and in order among Claude's; an output that isn't a pipe gets them through a file `phone-agent` copies in. Droid grants itself drawing over other apps and exact alarms through `appops` (as root or the shell user) the first time a page or wake-up needs them (exact alarms again on later wake-ups until granted). The app writes its scripts (`droid`, `phone-agent`, `droid-engine`, `android`, `shot`, the rest of `bin/`, and `vd-start.sh` and `vd-stop.sh` beside the Linux) at its first run after starting, so a newer app's need no Setup Update.
- **`VdHelper`** (in this APK, started with `app_process` as the shell user, like scrcpy) owns the hidden display, the same size as the phone's screen. When the agent runs `shot`, the helper waits for the display to settle (no new frame for 0.4 s, at most 2 s: a map or a video never stops), then saves a screenshot. `shot --text` lists the display's words, fields and buttons with where to tap each instead: the helper reads them through a `UiAutomation` of its own, connected for the ~15 ms it takes without pausing the owner's accessibility services, and writes them as Android's `uiautomator dump --windows` would (an option its help leaves out), which `shot` falls back on (2-3 s: it starts a Java process and waits for a second of quiet). The helper streams JPEG frames to the app's Watch view on a free local port (127.0.0.1), bound before the helper prints it. Any app may listen on or connect to a local port, so the app and the helper each prove they know that task's random token without sending it (HMAC challenges each way, as with the bridge), and the app then says `v WIDTH FPS` for frames at most WIDTH pixels wide and FPS a second (the chat's screen asks for 540 px at 2 a second, Watch for full size); it then also gets what is in front on the display (`IActivityTaskManager`, read when it connects and polled once a second while anyone watches), right away and whenever it changes: `[negative length][package name]`, or `Int.MIN_VALUE` for no app. On the same connection Watch's take over sends touches (`d|m|u X Y`, `c` to cancel), keys (`k KEYCODE`) and what the owner types with their own keyboard (`t TEXT`, as the key presses that type it), which the helper injects into its display through `InputManagerGlobal`, as `input -d` does. The chat keeps each turn's last frame, small, in `files/stills/` ([`ScreenWindow.kt`](../app/src/main/java/com/adetkov/droid/ScreenWindow.kt)), so the turn still shows it after the screen is gone. The helper also ends by itself when phone-agent is gone without stopping it (killed, say), or when an update replaces its APK, so a display can't keep the phone awake after its task. Makers' Android differs from Google's in what the helper meets: it sets up its process the way scrcpy does (an `ActivityThread` with a configuration controller, the shell's app info and an `Application`; Samsung's display code reads the configuration, scrcpy issue 4467), and a display option the phone refuses (touch feedback off, keyboard focus kept, own focus, own display group, always unlocked, trusted, in that order) is dropped rather than failing the display, which then does a little less. When it can't start at all, `vd-start.sh` says why (the helper's `error=` line, the shell's own error, or that it ended or didn't answer in 15 s), and so does the task's message. Setup starts one display itself, asks it for a screenshot and ends it ([`vd-check.sh`](../app/src/main/assets/setup/vd-check.sh), run from the app's assets; once per Droid version and Android build, whenever Setup is opened, and for diagnostics, one at a time), so a phone that refuses it shows why there, with diagnostics to copy, instead of failing every task. A helper that ends without a word gets Android's reason from the system log (a crash's signal, or a kill), and `vd-stop.sh` ends only a process that is a display helper.
- **Holding the screen**: after an answer, if an app is in front on the run's screen (the app asks the helper, `screenInUse` in [`ScreenFeed.kt`](../app/src/main/java/com/adetkov/droid/ScreenFeed.kt)), the app keeps the run's stdin open for 10 minutes (`HOLD_FOR` in [`Runner.kt`](../app/src/main/java/com/adetkov/droid/Runner.kt); paused while Watch is open), so a reply goes to the same process on the same screen. Then it closes stdin and the agent exits (one still up 30 s later is killed, unless it went on to a message sent meanwhile; while it exits, the service stays up, as "Finishing up…") and the display goes with what was on it (`DESTROY_CONTENT_ON_REMOVAL`); a later reply starts a fresh `--resume` run on a new screen. A held screen sleeps while no one views it: the app tells the helper it's held (`holdScreen`, a `h 1` line; `h 0` when a message comes), and the helper puts its VirtualDevice to sleep (`goToSleep`) while no client is connected, waking it for a viewer (the chat's live screen, Watch) or the agent's `shot` (which also ends the hold). Awake, a hidden display's own display group keeps the whole phone from suspending; asleep, the phone dozes as usual (checked on a Pixel 6a). It keeps the foreground service and an ongoing notification (countdown, Watch, Close screen) up; so an answer with nothing on the screen ends the run at once. The run also ends by itself if the app can't end it: the app's `su` client going doesn't end a run (stdin never reaches EOF), so a run whose app was killed (low memory, a crash, an update), frozen, or lost track of it used to keep its screen, and the phone, awake for hours. The app leases each run ([`Proc.lease`](../app/src/main/java/com/adetkov/droid/Backend.kt): a `{"type":"lease","until":EPOCH_SECONDS}` line on stdin that `phone-agent` keeps to itself), renewed every minute while it's working or watched (`LEASE_FOR`, 150 s), and, once it answers, until its screen closes plus 30 s (`LEASE_SLACK`), sent at once; when a lease runs out with no newer one or message, `phone-agent` closes Claude's stdin, Claude finishes what it was doing and exits, and the display goes. A message keeps a run for at least 150 s; a prewarmed one still waits 3 minutes for its first.
- The model choice is passed as `phone-agent --model <alias>`; `phone-agent` hands its arguments to `claude -p`. A `--resume` of a session this Linux doesn't have (after switching between root and Wireless debugging, or reinstalling the Linux) starts a new session instead of failing, and the chat notes it.
- Attachments are copied into the app's own shared-storage folder, `Android/data/com.adetkov.droid/files/uploads/<id>/`, which other apps can't read. The message tells the agent where each one is, as `[Attached: /sdcard/Android/data/…]` (a picture from Droid's camera as `[Photo I just took: …]`): `enter.sh` bind-mounts shared storage at the chroot's `/sdcard`, and root (or the shell user, whose groups include `ext_data_rw`) can read app folders there.
- **The camera** is the phone's own camera app (`ACTION_IMAGE_CAPTURE`, [`Attachments.kt`](../app/src/main/java/com/adetkov/droid/Attachments.kt)): it writes its picture straight into an attachment's slot through Droid's FileProvider (`external-files-path` `uploads/`), and a picture not taken leaves nothing behind. Droid asks for the camera permission first only because it holds it (for the agent's pages, which may ask for the camera from a tap), and Android won't let an app that declares it open another app's camera without it. The assistant panel's Camera chip takes one the same way; its picture goes with the request in place of the screen.
- **Speech** ([`Voice.kt`](../app/src/main/java/com/adetkov/droid/Voice.kt), [`Speech.kt`](../app/src/main/java/com/adetkov/droid/Speech.kt), [`Turn.kt`](../app/src/main/java/com/adetkov/droid/Turn.kt)), with sherpa-onnx: Silero VAD hears speech and pauses; NVIDIA Parakeet Unified EN 0.6B (int8, greedy search) transcribes the whole utterance about once a second while you talk (one pass at a time, always of the latest audio, and spaced to twice as long as the last pass took, so a long request neither queues passes nor keeps the cores busy throughout), with half a second of silence appended so it punctuates the end as an end. At each pause (a quarter of a second without speech) the transcription runs once more, and meanwhile Pipecat's Smart Turn v3.2 (8 MB, a Whisper Tiny encoder with a classifier, on the last 8 s) says how likely you're done. Both done (Smart Turn over 0.5, and the transcript ends a sentence, or Smart Turn over 0.95, and in either case not on "and", "the", "um" and the like) ends the turn after 0.9 s of silence (see [End of turn](#end-of-turn)); neither, after 2.5 s; otherwise after 1.2 s, as before. The transcript at that pause is the final one. Smart Turn's input is Whisper's log-mel features, computed in Kotlin exactly as Pipecat's `inference.py` makes them (checked against transformers in `TurnTest`), and the model runs on the onnxruntime that sherpa-onnx ships, through `libturn.so` ([`turn.c`](../app/src/main/cpp/turn.c), which finds it at run time), so the APK carries one copy of it. A phone set up before Unified keeps Parakeet TDT 0.6B v2 until Settings → Setup and updates → Voice → **Update** (500 MB; `models/parakeet/model.txt` names the model). With a Bluetooth headset connected, `AudioMic` asks Android for its mic (`setCommunicationDevice`) and gives it back when listening ends, so the answer read aloud plays in full quality; until the headset's link is up (a moment) it records from the phone. On a Pixel 6a: the recognizer loads in about 3.4 s and holds ~750 MB (loaded with the first word, freed once unused for 3 minutes, wherever Droid is), transcribes 4 s of speech in about 0.5 s, and Smart Turn judges in 75–250 ms.
- **Voice match** ([`VoiceMatch.kt`](../app/src/main/java/com/adetkov/droid/VoiceMatch.kt)): NVIDIA TitaNet small (sherpa-onnx's ONNX export, checked against its SHA-256) turns speech into 192 numbers. Enrollment averages six read sentences into a voiceprint, kept in the app's private `files/voiceprint.txt` with the model's name. On the lock screen, a request whose cosine similarity to the voiceprint is at least 0.50 is sent without unlocking. A miss, speech under 1.5 s, or a 4th try after 3 misses goes to the fingerprint as before. The miss count starts over when the phone is unlocked (Android's `USER_PRESENT`, whatever app it unlocks to), and when one of Droid's screens resumes only if the keyguard itself says the phone is unlocked: Android briefly resumes an app's other activities behind the lock screen when the assistant panel closes, so "an activity resumed" doesn't mean "unlocked".
- The assistant is a `VoiceInteractionService` ([`AssistService.kt`](../app/src/main/java/com/adetkov/droid/AssistService.kt)) whose session has no window: it opens the panel and, over an app, receives the screenshot Android takes before the panel appears. The screenshot becomes an attachment, sent as `[Screenshot of my screen: /sdcard/…]`. Android keeps the service bound, so Droid's process stays running.
### Without root

- **Pairing** ([`adb/`](../app/src/main/java/com/adetkov/droid/adb)): Droid's own small adb client: TLS 1.3 with a
  self-signed certificate for its RSA key, the exported keying material tied into SPAKE2 (a BigInteger implementation
  of BoringSSL's, checked against adbd), and the key sent as adb's PeerInfo. [`PairingService`](../app/src/main/java/com/adetkov/droid/PairingService.kt)
  finds Settings' pairing dialog by mDNS (`_adb-tls-pairing._tcp`, only at this phone's own addresses) and asks for
  the code in a notification, since the dialog closes when you leave Settings.
- **What Droid can tell of Developer options** ([`DevSettings.kt`](../app/src/main/java/com/adetkov/droid/DevSettings.kt)):
  Android 17 tells apps 0 for `development_settings_enabled` and `adb_enabled` whatever they are (and some of its builds
  for `adb_wifi_enabled` too), so there a 0 means "can't tell" and only a 1 counts. Wireless debugging is on while this
  phone announces `_adb-tls-connect._tcp`; Developer options are on while adbd runs (`init.svc.adbd`) or Wireless
  debugging does, and otherwise by how Settings takes their page: while they're off it closes it at once.
  `DevOptionsActivity`, a window-less screen every "Open Settings" goes through, opens the page and watches: back in
  front within 2 s means off, so it opens About phone at Build number instead; out of sight means on. Pairing's steps
  come from these, and `AdbHelper` looks for the announcement before switching Wireless debugging on, and off again
  only if it switched it on. A debug build acts so on any Android with `adb shell setprop debug.droid.hidesettings 1`.
- **The helper** ([`Bridge.java`](../app/src/main/java/com/adetkov/droid/Bridge.java)): over one adb connection
  (`_adb-tls-connect._tcp`), Droid grants itself `WRITE_SECURE_SETTINGS` and starts `app_process … Bridge` as the shell
  user in its own session. The bridge runs shell commands for the app on 127.0.0.1, streaming stdin, stdout, stderr and
  the exit code; both sides prove they know a random token (HMAC challenges each way), which is never sent. The bridge
  stays in adbd's cgroup, and Android stops adbd, and that whole cgroup, when neither USB nor Wireless debugging is on;
  so the launch first turns USB debugging on. Droid's own requests carry on when the app goes away (their output is dropped), as with root; the agent's `android` ends like a command in a pipe when its caller goes, and stops its command when it is stopped. The bridge then runs until the phone restarts, without Wi-Fi or Wireless
  debugging, unless USB debugging or Developer options go off. A bridge that isn't listening within 30 s is killed, and
  Droid pings it before using it.
- **After a restart** ([`HelperJob`](../app/src/main/java/com/adetkov/droid/HelperJob.kt)): once there is Wi-Fi, Droid
  switches Wireless debugging on, connects, starts the bridge, switches it off again and checks that the bridge still
  answers (a few seconds). On a Wi-Fi network Wireless debugging doesn't trust yet, Android asks first; if nobody allows
  it, Droid doesn't ask again on that connection until you tap Start in Setup. After an app
  update it starts a bridge with the new code, but only while the old one runs nothing. Until the helper runs (say,
  after a restart away from Wi-Fi), the chats stay open and a task says what it's waiting for.
- **Is it adbd?** adbd's certificate for connections changes with every boot, so it can't be pinned, and any app may
  advertise a port under adbd's mDNS name. So the launch command also writes a fresh nonce into Droid's own
  `Android/data` folder, which the shell user may write and other apps may not; without it, Droid never uses the token.
- **Linux**: Alpine in `/data/local/tmp/droid/rootfs`, where the shell user may run programs, under proot (Termux's
  fork, built from source by [`tools/proot/build.sh`](../tools/proot/build.sh) and carried in the APK as `libproot.so`).
  `android` reaches the bridge with `droid-bridge` (Python); `shot` reads the display's folder, bound at its own path.

- Inside Alpine, `android '<command>'` runs a command in Android as root, or as the shell user without root. In a task, its `am start` and `input` act on the task's hidden display unless the command names one (`--display 0`, `-d 0`: the owner's screen), so an app the agent opens or a tap it makes can't land on the owner's screen by accident: shell functions [`android`](../app/src/main/assets/setup/bin/android) puts ahead of the command, in Android's shell, so they hold with root or without. Beside `shot`, two general commands act on what `shot --text` lists: `tap LABEL` taps the control of that name (its whole name, any case; a name in two places, or only part of one, taps nothing and says what's there), and `fill [FIELD] TEXT` has the helper set a text field at once through accessibility (`ACTION_SET_TEXT`: any language, no keyboard; the field named FIELD by its hint, label or the words inside it, else the one with the cursor), then says what it holds. With Claude, reading `/tmp/screen.png` shows the screen in one step: `phone-agent` gives Claude a hook before each Read (`--settings`), and `shot --hook` takes the shot then and points the Read at it (the other engines' brief leaves that line out). A web page is read out only once something asks, so the helper gives an empty one up to a second to fill in. The agent gets nothing else: no per-app tools or recipes. It works the phone out from the screen's text and pictures, and a shell.

### Agent engines

`phone-agent --engine claude|codex|opencode` (Claude if omitted). Codex and OpenCode have no stream-json input, so `droid-engine` (Python, in the chroot) runs `codex exec --json` / `opencode run --format json` once per message and prints Claude's stream-json subset (init, assistant text and tool_use with a short description, result), so the app's parser is unchanged. A message sent mid-turn is queued and sent as the next turn of the same session, with an answer of its own (Claude instead takes it into the turn it's in). Closing stdin, the 3-minute first-message wait and SIGTERM behave as for Claude.

| | Claude Code | Codex | OpenCode |
|---|---|---|---|
| Install | claude.ai installer | GitHub release, `*-unknown-linux-musl` | GitHub release, `opencode-linux-{arm64,x64-baseline}-musl` |
| Sign-in | paste-the-code OAuth | ChatGPT device code (`codex login --device-auth`) or API key | provider API keys (`auth.json`); free models need none (the default until you add a key: each run, a free one from `opencode models` that calls tools and sees images, as they come and go; after that OpenCode chooses) |
| Screenshot | `Read` on the PNG, or on `/tmp/screen.png` (taken by a hook as it's read) | `view_image` tool | `read` tool, needs a vision model |
| Session data | `~/.claude/projects/-root/ID.jsonl` | `~/.codex/sessions/**/rollout-*-ID*.jsonl` (older ones `.jsonl.zst`), and its SQLite (`codex delete ID`) | `~/.local/share/opencode/opencode.db` (`opencode session delete ID`) |
| Instructions | `~/.claude/CLAUDE.md`, plus `--append-system-prompt-file` | `~/.codex/AGENTS.md` (all three, written at each start) | `~/.config/opencode/AGENTS.md` (the same) |

Codex runs with its sandbox off and OpenCode with `--auto`: the chroot is the boundary. Recorded event streams for the adapter tests are in `app/src/test/resources/engines`.

### Android findings

- **Plain virtual displays sleep with the phone on Android 17**: every virtual display joins the default display group, and `VIRTUAL_DISPLAY_FLAG_OWN_DISPLAY_GROUP` is ignored. A display on a **VirtualDevice** (`LOCK_STATE_ALWAYS_UNLOCKED`) gets its own group and keeps running while the phone is locked. That needs a companion association: `cmd companiondevice associate USER PACKAGE MAC PROFILE` takes positional arguments, despite its help text. `cmd companiondevice list` prints `Association{mId=…, mDeviceMacAddress=…}` on Android 17 but a table (`ID | Package Name | Mac Address`) on Android 15; reading only the first left Android 15 waiting 3 s for an association that was there, then on a plain display. Without one, Droid falls back to a plain display with its own display group, which works on Android 16 and earlier (untested).
- **The agent's tools can starve Android**: what runs in the chroot is invisible to Android's low-memory killer, so when a tool takes the RAM, Android closes apps instead, Droid's too (despite its foreground service). The agent goes on and finishes, but Droid's restarted app shows the chat as "Interrupted" and posts no notification. Seen with ImageMagick: `montage` of 45 camera photos peaked at 4.07 GB on a 6 GB phone and emptied it. `phone-agent` now caps ImageMagick (`MAGICK_MEMORY_LIMIT=256MiB`, `MAGICK_MAP_LIMIT=512MiB`, `MAGICK_AREA_LIMIT=64MP`): 0.59 GB, nothing killed. Other heavy tools aren't capped; a memory cgroup for the chroot would cover them, and Droid doesn't yet pick up a run that outlived its app.
- A display on a VirtualDevice keeps the whole phone awake: its own display group stays on, so PowerManager holds its display suspend blocker and the phone never suspends, though the phone's own screen is off. Battery stats show no wakelock for it, only "Interactive" time well above "Screen on" time.
- **There is one keyboard, and it goes with the phone's focus.** Opening an app on the hidden display (`am start --display`), or tapping there, made it the top-focused display: the keyboard left the owner's screen mid-sentence and came up on the agent's. The display is now made with `VIRTUAL_DISPLAY_FLAG_STEAL_TOP_FOCUS_DISABLED` (with `OWN_FOCUS`, which it needs; a VirtualDevice keeps it on Android 17), so it never takes the phone's focus. Its apps still have their own focus, and key presses aimed at the display (`input -d N text`/`keyevent`) reach them, but no keyboard ever shows there; take over types through the owner's own keyboard instead (Watch's keyboard button, sent as `t TEXT` and `k KEYCODE`). Before that, `IWindowManager.setDisplayImePolicy` (local) at least kept the agent's keyboard drawn on its own display.
- Toybox's `mount --make-rprivate` exits 0 and changes nothing, so `enter.sh` uses the root manager's busybox, and refuses to mount if the namespace is still shared.
- Alpine needs `USE_BUILTIN_RIPGREP=0` and `libgcc libstdc++ ripgrep` for Claude Code.
- The assistant role can't be requested with a dialog. Setup grants it as root or the shell user (`cmd role add-role-holder`).
- **The shell user may not make named pipes or hard links** (SELinux), and proot's fake root reports success for both
  (`mkfifo` then makes nothing). So `phone-agent` feeds Claude through an ordinary pipe, and proot's `--link2symlink`
  fakes hard links. Upstream proot can't do the `O_TMPFILE` + `linkat("/proc/self/fd/N")` that apk 3 writes every
  file with ("failed to write database"); Termux's fork can.
- **Other ways around root are closed on Android 16 and 17** (from their framework code): `cmd role
  set-bypassing-role-qualification` used to let an ordinary app hold the companion app-streaming role (its own
  trusted, always-unlocked displays, no adb afterwards), but Android 16 ignores the bypass for the app-streaming and
  nearby-streaming roles; the role that still allows it grants only `CREATE_VIRTUAL_DEVICE`, so its displays are
  untrusted and take no input. An app's own virtual display hosts only activities that opt in (`allowEmbedded`).
  Android 17's Computer Control (the API behind background agents) needs a privileged permission and Google's allowlist.
- **Android 17 gates mDNS**: without `ACCESS_LOCAL_NETWORK` (Nearby devices), each `NsdManager` search opens a "Choose a
  device to connect" picker. Wireless debugging trusts a network by BSSID or SSID, so "Always allow" covers a campus's
  many access points; it needs Wi-Fi, and turning it off doesn't end processes started through it while USB debugging keeps adbd running (it does when neither is on: seen on an Android 16 emulator).
- **Screenshots for the assistant on Android 17**: an assistant targeting API 37 gets only the context its `voice-interaction-service` XML declares (`usesAssistData`, `usesAssistScreenshots`, `usesAssistStructureScreenContent`). Without them, long-press shows the session with no screenshot. Asking again from the session with `show()` doesn't help either: Android strips data flags from an assistant's own requests. The screenshot also needs "Use text from screen" (`assist_structure_enabled`) on, because Android skips it when assist data isn't allowed. Droid doesn't declare `usesAssistStructureScreenContent`, so that setting still gets it no text from the screen.
- **The screenshot can come before the show**: when no screenshot is allowed ("Use screenshot" off), Android hands the session its null screenshot synchronously, before it sends the show itself. A `hide()` at that point removes the show still queued, so long-press only vibrates. The session therefore keeps a screenshot that comes before `onShow` for `onShow` to handle.

### Speech-to-text model

Word error rates with sherpa-onnx 2.0.2, greedy search, 4 threads, text normalized with Whisper's English normalizer: 300 utterances each of LibriSpeech test-clean and test-other; the same clean ones with three other LibriSpeech talkers mixed in at 10 dB ("babble"); and real spoken requests to a voice assistant from SLURP (900 recordings, headset and far-field mics). [`tools/asr_eval.py`](../tools/asr_eval.py) runs it all again (its docstring says how).

| model (sherpa-onnx's int8 export) | clean | other | babble | SLURP |
|---|---|---|---|---|
| **Parakeet Unified EN 0.6B** (used) | 1.48% | 2.85% | 3.37% | 14.97% |
| Parakeet TDT 0.6B v2 (before) | 1.55% | 3.05% | 3.75% | 17.58% |
| Parakeet TDT 0.6B v3 (multilingual) | 2.17% | 4.62% | 16.6% | 21.48% |
| Moondream Parakeet Ultra | 1.89% | 3.87% | 3.82% | 19.44% |
| Moondream Parakeet Redux (327 MB download, same 652 MB unpacked) | 2.65% | 6.01% | 5.66% | 31.26% |
| Parakeet TDT 110M (130 MB, a drop-in) | 2.24% | 5.07% | 6.27% | 20.75% |
| Parakeet TDT-CTC 110M, CTC head (126 MB) | 2.65% | 5.94% | 7.06% | 22.36% |
| Moonshine base (2026-02-27 quantized, 135 MB) | 2.99% | 8.50% | 12.38% | 37.89% |
| Moonshine tiny (2026-02-27 quantized, 42 MB) | 4.29% | 13.03% | 23.39% | 51.09% |

The small models (checked 2026-11-23, when a 0.6B model's ~750 MB and its time on long requests were in question) are 2.5–10× faster on a desktop CPU but all significantly worse everywhere: on SLURP the best, the 110M drop-in, makes 5.8 points more errors (95% interval 4.5–7.0), and far-field requests suffer most (26% against 17%); Moonshine falls into repeated-phrase loops on real requests. So Droid keeps the 0.6B, and makes its cost small instead: one pass at a time, and freed when unused (see Speech above). Unified is significantly better than v2 only on SLURP, the closest to how Droid is used (2.6 points, 95% interval 1.5–3.8). The released Ultra predates sherpa-onnx's fix keeping its convolutions in float32 when quantizing (PR #4179); rebuilt that way it did best of all (SLURP, first 300: 13.91%; babble 2.74%), so it's worth another look once sherpa-onnx republishes it. Every encoder is 652–654 MB, so none loads faster.

**Hotwords** (nudging the recognizer toward names you use: contacts, apps) were tried and left out. In sherpa-onnx they need beam search, which on a Pixel 6a is 2.5–4 times slower than greedy for this model, even with one or two paths (4.4 s of speech: 1.3 s greedy, 3.7 s with one path, 4.1 s with two), and every transcription is on the way to sending. They do work when the names are said (LibriSpeech's rare-word lists: v2's error on those words falls from 6.8% to 2.0%), but a list of names that weren't said makes things worse (v2 on SLURP: 16.3% → 18.8%, by turning words into names: "Sarah" → "Savannah", "Jack" → "Jackson"). sherpa-onnx also splits 31% of words into different word pieces from the model's own tokenizer, so hotwords would have to come pre-split.

### End of turn

Smart Turn v3.2 and the transcript's last word were scored on 2,630 English clips of Pipecat's public test set (smart-turn-data-v3.2-test; human speech and TTS; each clip ends where the speaker stopped or paused mid-thought). Counted: "cut off", unfinished clips judged finished (the costly mistake), and "made to wait", finished ones judged unfinished, reweighted to the whole English set.

| rule | cut off | made to wait |
|---|---|---|
| Smart Turn over 0.5 | 7.3% | 3.2% |
| the transcript ends a sentence (. ? !) | 50% | 1.4% |
| both, and not on a word people go on from | 5.2% | 5.3% |
| **that, or Smart Turn over 0.95 and not on such a word** (used) | 5.3% | 4.6% |

Parakeet ends most clips with a period, fragments included ("Rinse your um mouth with."), so the transcript can only veto Smart Turn; and short commands often come without one, hence the second way. Clips judged unfinished by both wait 2.5 s; the rest keep the old 1.2 s. On six SLURP requests replayed on the Pixel through the voice loop (a debug hook, below), finished requests ended after 0.54–0.96 s of silence (0.76 s on average) instead of 1.22 s, and a pause mid-request ("...to my friends Divia [pause] How are you?") was waited through.

That scores one pause at a time. A whole request has several, and at first a pause both called finished ended it as soon as they had answered, about 0.6 s after the last word: people were cut off mid-request. [`tools/turn_sim.py`](../tools/turn_sim.py) runs the whole loop frame by frame with the real models (Silero, Smart Turn, Parakeet, the judgment landing 320 ms after a pause, as on a Pixel 6a) over 900 SLURP requests and 300 LibriSpeech test-clean passages of 8 s or more, each also through a simulated Bluetooth headset (8 kHz and back, plus a noise gate). Cut off: it stopped with more speech to come; latency: silence after the last word until it stopped (median / mean).

| when both say finished, stop after | SLURP | SLURP, Bluetooth headset | LibriSpeech, long passages | LibriSpeech, Bluetooth |
|---|---|---|---|---|
| their answer (about 0.6 s) | 1.0% cut off · 0.61 / 0.77 s | 2.3% · 0.67 / 0.86 s | 24% · 0.61 / 0.92 s | 33% · 0.67 / 0.97 s |
| 0.7 s of silence | 0.8% · 0.70 / 0.85 s | 2.3% · 0.77 / 0.93 s | 16% · 0.70 / 0.98 s | 21% · 0.77 / 1.01 s |
| **0.9 s** (used) | 0.4% · 0.93 / 1.03 s | 1.8% · 0.99 / 1.11 s | 5.0% · 0.93 / 1.14 s | 8.7% · 0.99 / 1.12 s |
| 1.0 s | 0.4% · 1.02 / 1.10 s | 1.4% · 1.09 / 1.18 s | 4.0% · 1.02 / 1.21 s | 5.7% · 1.06 / 1.17 s |

Almost all the cut-offs were real pauses of 0.6–1.1 s after words that sounded finished, and were ("Remove from my calendar meeting" | "at nine am", "Were the stocks rising?" | "or declining"), so only waiting longer helps: a stricter Smart Turn threshold barely did (24% to 22%), and neither did VAD hysteresis or asking again. With the fixed wait, how quickly the phone answers no longer matters (the old rule cut off 24% at 320 ms but 6% at 600 ms, so a busy phone cut off less). LibriSpeech is read aloud and counts a whole passage as one request, so it overstates the cut-offs; it shows the trend. Over the Bluetooth channel, the Silero model Droid uses (sherpa-onnx's, v4) hears only half of SLURP's speech frames (v5 and v6 about 90%): narrowband cuts the ends off words.

### Voice match model

Tested on LibriSpeech test-clean (40 speakers): each speaker enrolled with 6 five-second clips, then tested with clips of other utterances against every voiceprint (~800 genuine and ~31,000 impostor trials per row). Error rates are at the equal-error threshold; "babble" mixes in three other talkers at 10 dB SNR.

| sherpa-onnx model | 1.5 s | 2.5 s | 4 s | 2.5 s + babble | ms per 5 s (desktop CPU) |
|---|---|---|---|---|---|
| **nemo_en_titanet_small** (38 MB, used) | 0.75% | 0.37% | 0.12% | 2.3% | 190 |
| nemo_en_titanet_large (96 MB) | 0.90% | 0.38% | 0.25% | 1.8% | 500 |
| 3dspeaker eres2net_sv_en_voxceleb (25 MB) | 1.1% | 0.52% | 0.37% | 2.4% | 545 |
| wespeaker resnet34_LM (25 MB) | 11.5% | 7.0% | 5.1% | 33% | 390 |
| wespeaker CAM++_LM (27 MB) | 45% | 46% | 45% | 45% | 250 |

The WeSpeaker models do far worse through sherpa-onnx 1.13.8 than their published numbers; CAM++ is at chance, probably a feature mismatch. LibriSpeech's speakers each used their own microphone, which makes impostors easier to tell apart than on one phone's mic, so expect more errors in real use. TitaNet small embeds a 4 s request in 90–160 ms on the x86_64 emulator.

Clones: Pocket TTS, given one 10 s clip of each speaker, said three short commands (120 clips). Against the speaker's own voiceprint they scored 0.34 on average (others' voiceprints: 0.06); 6.7% reached 0.50 and 18% reached 0.45.

## Build

Needs JDK 17 or later and the Android SDK (`ANDROID_HOME`, or `sdk.dir` in `local.properties`).

```sh
./gradlew assembleDebug        # app/build/outputs/apk/debug/app-debug.apk
./gradlew testDebugUnitTest lintDebug
./gradlew assembleRelease      # signed if keystore.properties exists (storeFile, storePassword, keyAlias, keyPassword)
tools/proot/build.sh --source proot-source.tar.gz  # the exact proot and talloc sources the APK's proot is built from
tools/proot/build.sh           # rebuilds app/src/main/jniLibs/*/libproot.so from source (needs the NDK)
```

The first build downloads the sherpa-onnx AAR from its GitHub release into `app/libs/`, checked against the SHA-256 in `app/build.gradle.kts`. Debug builds on an emulator replay a canned agent with a fake hidden screen, so the UI can be worked on without a phone (to replay a real run, put its frames and scripts, one per turn, in Droid's `files/fake-screen`: see [`FakeScreen.kt`](../app/src/debug/java/com/adetkov/droid/FakeScreen.kt)); `adb shell setprop debug.droid.real 1` (then restart Droid) makes an emulator a phone without root, Wireless debugging and all (an emulator's Wi-Fi is "AndroidWifi"). Debug builds also take `am broadcast -n com.adetkov.droid/.AdbTestReceiver -a pair|shell|ensure|asr|listen|update-speech` from adb (see `AdbTestReceiver.kt`): `asr` transcribes a 16 kHz WAV and says what Smart Turn makes of it, `listen` runs the voice loop on one and logs how long after its end the turn was over. The build compiles `libturn.so` with the NDK (the version in `app/build.gradle.kts`; Android Studio or `sdkmanager` installs it).

Pushing a tag such as `v0.9` runs [`release.yml`](../.github/workflows/release.yml): tests, lint, the release APKs (signed with the repository's `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS` and `KEY_PASSWORD` secrets; without them it stops, and the tag must match `versionName`) and proot's source archive, drafted as a GitHub release. Every release has to be signed with the same key, or phones can't update to it.
